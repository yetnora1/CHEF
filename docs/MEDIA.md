# Media library and Supabase Storage

`/admin/media` (`media.write`) holds **every photo and video on the website**, each with Edit and
Delete: the files bundled with the site, uploads, and videos. Files are described per language, and
uploaded images are chosen in content forms. An uploaded image is **private by default**: visible to
visitors only while published content uses it, and no longer once that content is unpublished. Decisions:
[ADR 0004](adr/0004-stage-3-cms.md) §3–4. Content model: [CMS.md](CMS.md).

## Three kinds of file, one library

Every file is one `media_assets` row (`status`, `kind`, `bundled_key`, `removed_at`), so titles,
descriptions, Amharic review, versioning and the audit log work the same for all of them.

| File                                       | Where the bytes are                      | Visitors see it                      | Delete                                                        |
| ------------------------------------------ | ---------------------------------------- | ------------------------------------ | ------------------------------------------------------------- |
| Bundled (`status = 'bundled'`)             | `src/assets`, `public/videos` (the code) | Unless deleted                       | `removed_at`: off the site at once, and restorable            |
| Replacement of a bundled one (`ready`)     | Storage, in the same row                 | Unless deleted                       | The upload is deleted for good; restoring brings the original |
| Uploaded image (`ready`, no `bundled_key`) | Storage                                  | While published content uses it      | For good; refused while content uses it                       |
| Uploaded video (`kind = 'video'`)          | Storage                                  | At once, in the homepage's video row | For good                                                      |

**Bundled files stay in the code.** The site is built from them and its files are read-only at run
time, so "deleted" means "not shown": `public_site_media()` tells the public pages which are gone
(`src/features/cms/site-media.ts` applies it to the catalogue in
`src/features/content/bundled-media.ts`). To remove the bytes themselves, delete the file from the
repository. If the database cannot be read, the site falls back to its bundled files, so a deleted one
comes back for the length of the outage (failed reads are retried within minutes). Never rely on Delete
for a photograph that must disappear for legal or privacy reasons: remove it from the code as well.

A deleted slot closes up rather than showing a placeholder: the hero and the About and story cards give
their space to the text, dish and service cards keep their text, the homepage mosaic takes the next
photograph not on the page yet, and the credits page drops a sample that is no longer used. An upload with
a recorded credit is listed on `/credits`, since these slots carry no caption.

**Adding a bundled file** needs a migration as well as the code: a row with the same `bundled_key` and
English description. `tests/integration/db/site-media.test.ts` fails if the two differ.

## Storage layout

| Item         | Value                                                                                                                                                                                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bucket       | `media`: **private** (`public = false`), 50 MB limit for videos, `image/jpeg`, `image/png`, `image/webp`, `video/mp4`, `video/webm` only (images stop at 10 MB in the upload route and the `media_assets_size_range` constraint) |
| Object names | `assets/<asset uuid>/<32 random hex>.<jpg\|png\|webp\|mp4\|webm>`, generated by the server, never reused                                                                                                                         |
| Database row | `public.media_assets`: `storage_path` (current file), `pending_path` (reserved upload), type, size, dimensions, title, credit, `status` `pending` → `ready` (or `bundled`, see above), `kind`, `version`                         |
| Alt text     | `public.media_asset_translations` per locale (1–300 characters); visitors get Amharic alt text only once its review is confirmed, English otherwise (marked `lang="en"`)                                                         |
| Created by   | migrations `20261027090400_cms_media_storage.sql` (bucket and `storage.objects` policies), `20261104100000_site_media_library.sql` (videos, bundled files)                                                                       |

## Upload pipeline

```
browser ──multipart──▶ POST /api/admin/media (Route Handler)
   1. same-origin check (Sec-Fetch-Site / Origin vs host)            → 403
   2. Content-Length required, ≤ 10 MB + 64 KB                       → 411 / 413
   3. authorizeAdminRequest('media.write')                           → 401 / 403
   4. processImage(): magic bytes; declared type and extension must match the content;
      decode with a 40-megapixel and 8000 px limit; auto-rotate; resize to ≤ 2560 px;
      re-encode (JPEG q82 / PNG / WebP q82), sRGB; EXIF, GPS and other metadata dropped → 422 <reason>
   5. with the staff member's own session (never the secret key):
      reserve   insert media_assets (pending_path = new name)
      upload    Storage accepts the object only at a reserved name; never overwrites
      finish    storage_path := pending_path, status 'ready' (the database checks the object exists)
      alt text  optional English description
```

A photo over 4 MB is resized in the browser first, because Vercel Functions refuse a request over
4.5 MB and phone pictures are often bigger; the server then treats it like any other.

Only the re-encoded image is stored, so a file that merely looks like an image (polyglots, HTML or
scripts with an image extension, oversized "decompression bombs") is rejected or rewritten. It is a
Route Handler rather than a Server Action because server actions are capped at 64 KB to protect the
inquiry form. Replacing a file reserves a new name, uploads, switches the row (guarded by `version`)
and then removes the previous object; pages that use the image show the new file at once.

Every step can fail without exposing anything: an unfinished upload stays a private `pending` row,
and an object no row tracks any more stays private. Both appear in the library as "leftover files"
for `media.write` staff to clean up (`public.media_cleanup_candidates()`, uploads abandoned for over
an hour).

## Video uploads

A video can be up to 50 MB, more than a request to the server can carry, so the browser sends it straight
to Storage, as the signed-in staff member, at a name the server reserved:

```
browser: the file's type and size; it must be able to read the video's pixel size → message
   1. reserveVideoAction (media.write)   reserve a name on a new or existing row
   2. browser ──POST──▶ Storage          accepted only at the reserved name, only as an allowed type
   3. completeVideoAction (media.write)  reads the first bytes and the size through Storage:
                                         signature must match the extension, ≤ 50 MB; then the row
                                         points at the file (the database checks it exists)
```

A failed check removes the file and gives up the reservation. Videos are not re-encoded (there is no
video encoder in a Vercel Function) or scanned: staff with `media.write` are trusted to the extent of
the signature check, and the file is only ever served from Storage's own domain under its stored type.
A video has one file, so a large upload is also what the homepage's tiles load: short clips work best.

## Who can read, write and remove

Policies on `storage.objects` (bucket `media` only):

| Policy                                                         | Role                | Rule                                                                          |
| -------------------------------------------------------------- | ------------------- | ----------------------------------------------------------------------------- |
| `chief_media: staff read`                                      | authenticated       | `content.read` or `media.write`                                               |
| `chief_media: public read of images used by published content` | anon, authenticated | `private.media_object_is_public(name)`                                        |
| `chief_media: staff upload to reserved paths`                  | authenticated       | `media.write` and the name is some asset's `pending_path`                     |
| `chief_media: staff remove untracked files`                    | authenticated       | `media.write` and no asset tracks the name (`storage_path` or `pending_path`) |

There is no UPDATE policy (no overwrites, no renames). A file is public exactly when its asset is
`ready` and either belongs to the website itself and is not deleted (the replacement of a bundled file,
or a video), or is used by published content with a published translation: a service, a dish in a
published category, a journal cover, a page image slot, or a gallery photo. The same rule decides whether
the database shows alt text and credits to visitors. A used image cannot be deleted: the references are
`ON DELETE RESTRICT`, and the admin explains where the image is used. A bundled row can never be deleted
outright (its `DELETE` policy excludes it), so the website's files always have a row.

## Serving images

| Route                            | Who                             | Reads with                         | Cache                                               |
| -------------------------------- | ------------------------------- | ---------------------------------- | --------------------------------------------------- |
| `/media/assets/<id>/<file>`      | everyone                        | anonymous client (publishable key) | `public, max-age=300, s-maxage=300`; 404 `no-store` |
| `/admin/media/<id>/file?v=<ver>` | `content.read` or `media.write` | the staff member's session         | `private, no-store`                                 |

Both send `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none';
sandbox`, and only serve names matching the generated pattern. Public pages render images through
`next/image` (`images.localPatterns` allows only `/media/assets/**`, without query strings).

A video's URL answers with a redirect to a one-hour signed Storage link, made with the same client and so
under the same policies: players need range requests, and a Vercel Function cannot send a 50 MB response.
An unpublished or deleted file cannot get a new link, and deleting a video removes its object, so existing
links stop working too.

**After unpublishing**, browsers, CDNs and the Next.js image optimiser may keep a copy for up to
five minutes (`max-age=300`, `images.minimumCacheTTL = 300`); the optimiser's cache cannot be purged.
If an image must disappear immediately (for example a privacy request), unpublish it, then replace
or delete the file: a new object name is never in any cache, and the old object is removed.

## Hosted Supabase checklist

Not verified yet: no Supabase environment was available (see
[VERIFICATION.md](VERIFICATION.md#11-stage-3-cms)). On the dev project, after `supabase db push`:

1. **Bucket.** Storage → Buckets: `media` exists, is **not public**, 10 MB limit, the three image types.
2. **Policies.** On hosted projects `storage.objects` belongs to `supabase_storage_admin`; the
   migration's `create policy` statements rely on the platform's policy grants for `postgres`. Check
   that the four `chief_media:` policies exist (Storage → Policies, or
   `select policyname, cmd, roles from pg_policies where schemaname = 'storage' and tablename = 'objects';`)
   and that no other policy on `storage.objects` grants access to bucket `media`. If `db push` failed
   on these statements, stop and create them in the dashboard with exactly these definitions.
3. **Behaviour** (sign in as a `content_editor` test account):
   - upload a JPEG in `/admin/media`; the detail page says "Private";
   - `curl -i https://<ref>.supabase.co/storage/v1/object/public/media/<storage_path>` → not found
     (the bucket is private), and `curl -i <site>/media/<storage_path>` → 404;
   - use the image on a service and publish it → `/media/<storage_path>` 200; unpublish → 404;
   - deleting the image while it is used is refused; after removing it from the service, deletion
     removes the object (Storage → `media` no longer lists it);
   - an event manager or analyst account gets 403 from `POST /api/admin/media`;
   - upload a short MP4 in `/admin/media`: the progress bar runs, the detail page says "On the website
     now", it plays in the homepage's video row (`/media/<storage_path>` → 302 to a Storage link, and that
     link answers a `Range` request with 206); deleting it → 404, and the old link stops working.
4. **Keys.** Nothing in Storage uses `SUPABASE_SECRET_KEY`; leave the secret key out of the CMS.

## Limits and known gaps

- One size per image (≤ 2560 px); responsive sizes come from the Next.js image optimiser.
- No malware scanning beyond decoding and re-encoding; no animated images; no SVG.
- Videos: MP4 or WebM up to 50 MB, one file per video, no poster frame of their own (the first frame
  shows once the video loads), no re-encoding or trimming. No resumable upload: an interrupted one starts
  again.
- No bulk upload, folders or tags; search covers titles, credits and alt text.
- Bundled files' categories (events or dishes in the gallery) and order stay in the code.
- Files left by failed requests are removed only when staff run the cleanup.
